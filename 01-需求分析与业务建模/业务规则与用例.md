# 用例与业务规则

原始需求文档把系统用例分成两组：UC01–UC06 是预约与诊疗视图，UC07–UC12 是连锁运营管理视图，另外给了 T01–T10 一组验收测试点。逐条规约见根目录 docx，这里只记我在建模和实现时实际用到的部分。

## 用例分组

预约与诊疗这一组由前台和牙医配合完成：UC01 建患者档案与逐项过敏，UC02 安排跨店预约，UC03 处理改约、取消和未到诊，UC04 到诊登记与诊前核对，UC05 由牙医记录实际治疗项目，UC06 生成并核对结算单。文档里特意说明，患者取消和未到诊都在 UC03 处理，但要保留不同结果；账号和权限只是处理资料的基础条件，不是主要业务目标。

运营管理这一组由运营经理、财务和总部经理使用：UC07 维护牙医与资质的多对多关系，UC08 记录牙医在哪家诊所的哪些时段出诊，UC09 录入耗材成本和运营费用，UC10 按季度归集后提交核算，UC11 看取消率和治疗记录完整情况，UC12 维护权限和操作记录。

## 落到代码里的规则

| 规则 | 我是怎么处理的 |
|---|---|
| 同一时段不能被两个人约走（T02） | 给 `appointments.slot_key`（牙医＋日期＋起始时间）建唯一索引，并发提交时只有一个能成功 |
| 取消、改约要把时段还回去 | 取消后把 `slot_key` 改写成释放态，否则那个时段会被唯一索引一直占着 |
| false 不能直接算取消（T03） | 预约状态分成待到诊、已到诊、治疗完成、患者取消、诊所撤销、已改约、未到诊、待核实八种，是否到诊只是其中一个字段 |
| 价格要留快照（T06） | 治疗目录调价不影响历史单据，结算行里存的是当时的单价 |
| 一次就诊只能有一张有效结算单 | 按就诊号做幂等判断，配 `invoice_no` 唯一索引，重复提交返回已有单号 |
| 待分摊费用不能当 0（T08） | 共用费用先挂 UNALLOCATED，只要还有没分摊的，季度报表就不给出可分配结果 |
| 净利润与激励基金 | 收入扣耗材和运营费后算净利润，按 10% 计入激励基金，按季度核算 |
| 患者只能看自己的 | 小程序端接口强制校验微信 OPENID，越权返回 403 或 404 |
| 员工按角色分权限 | 员工端接口统一标记 STAFF_ONLY，服务端按角色做 ACL，页面上的写按钮也按角色隐藏 |

## 状态与留痕

预约的状态流转是「待到诊 → 已到诊 → 治疗完成」，旁路有患者取消、诊所撤销、已改约、未到诊和待核实。改约的做法是新增一条预约、把原单标记为已改约并记下关联，不删原单。每次新增或变更都记业务编号、操作者、时间和原因；业务没完成不能靠删除或覆盖来掩盖。

前台不能改牙医已经确认的治疗；已开单后发现漏项，走更正流程并保留版本，不在原明细上无痕补一行。经理能看到汇总，但不因为能看报表就自动获得全部患者的完整病历。

界面上用的是课程演示的中性说法，但代码里的字段、状态枚举和上面这些规则都按需求文档来，没有因为改文案而改模型。

## 一、先说一个范围问题

需求文档第 1.2 节、第 4.1 节都明确写：**「本期以内部员工操作为主，患者通过电话和柜台办理，没有患者自助登录端」**。

所以严格按文档，本系统应该是「员工端网页 + 后台」，患者小程序属于**文档外延伸**。作业要求两端都做成能实际打开的形态，因此保留了小程序，并在作业文档里写明它是延伸、主体业务仍按岗位分工放在员工端。

**结论：员工网页与云端业务规则是这份核对的主体；小程序按「市面同类患者端」的标准看交互是否完整，不拿它去套 UC 用例。**

## 四、按市面系统标准补充的部分

1. **可配置排班**：不再把所有牙医都当成全天在店，排班决定可约时段；没排班时沿用固定工作时间，保证老数据不受影响。
2. **操作记录视图**：任何业务变更都能按业务编号回溯，越权尝试也留痕，界面上能按操作者 / 结果 / 关键字查。
3. **季度核算审批流**：财务提交 → 经理审批 → 版本留存，能下钻到结算单号与费用凭证号，更正生成新版本而不覆盖已批准结果。
4. **数据导出**：预约管理页可导出当前查询结果为 CSV，导出范围与角色可见菜单一致。
5. **13 个视图 / 5 角色**：新增「出诊排班」「操作记录」「核算审批」「员工账号」，运营、财务、经理各看到自己该看的部分。
6. **断网提示**：网页只有云端数据源，断网时明确提示并保留当前数据，恢复后点「重连云端」即可继续，不伪造数据。

## 五、仍然存在的差距（如实列出）

这些不是 bug，是文档要求与「学生大作业可交付范围」之间的取舍，后续要继续做的话按此清单推进：

| 差距 | 文档依据 | 现状 |
|---|---|---|
| **患者自助端** | 1.2 / 4.1「没有患者自助登录端」 | 小程序是项目要求加的延伸，不在 UC 范围内；保留 |
| **25 张逻辑表 vs 11 个业务集合** | 第 10–11 章 | 按「一个集合 = 一个生命周期一致的业务对象」合并（另有 5 个支撑集合），理由写在 `02-数据模型/模型设计说明.md`；文档型数据库下不建物理外键，靠代码与唯一索引兜 |
| **治疗 / 结算更正版本链** | UC05 例外、UC06 例外、10.1 | 目前 `visitTreatment.remove` 直接删草稿行；结算单有 `version` 字段但未实现 `invoice_revisions` / `treatment_revisions` 的完整版本链与更正审批 |
| **费用分摊明细** | UC09、10.4 | 只做到「待分摊挂起 + 凭证防重」，没有按规则拆到多牙医并校验分摊合计等于来源金额 |
| **报表按诊所 / 牙医筛选与覆盖缺口提示** | UC11（文档标注 P1） | 目前按全局口径出取消率；筛选、下钻到单条预约、数据缺口标注未做 |
| **断网提交标识与恢复重试** | 7.2 | 前端有超时重试与自动重连，但没有「同一提交标识」保证断网恢复后不重复下单 |
| **迟到多久转未到诊可配置** | 3.3 场景 C、8.1 | `lateGraceMin` 是固定配置，没有经理审批后配置的界面 |
| **列表分页** | 市面系统惯例 | 单次查询有上限，前端未做分页控件；改用 CSV 导出查看全量 |
